# 《学习观》本体知识图 · 规范（草案，待确认）

> 目标：产出**仍然是知识图**（节点 + 关系，可存、可查、可导、可增补），但**节点类型与关系类型改用《学习观》的本体**，由 LLM 抽取生成。
>
> 本文件是抽取契约的规范。每一条都给出**原书出处**；凡属结构推断而非原书原话的，标注 `[推断]`。

## 0. 为什么不能靠本地重切

先前交付的「渐构模式」是对既有**命题图**做零成本再切分。它无法满足需求，原因是**两套本体之间没有函数关系**：

- 命题图的抽取目标是「把这段文本拆成命题与关系」，节点类型是 fact / claim / inference / concept / definition / example / counter_example / rule。
- 《学习观》的靶图要求「某知识点的输入空间 → 输出空间映射」，以及按**学习功能**分类的材料。

用实测数据说明这个不对齐（《学习观》原书自己那 3729 节点的命题图，重切后）：

| 材料 | 命中 / 2456 | | 材料 | 命中 / 2456 |
|---|---|---|---|---|
| 规律表述 | 2456 (100%，饱和无信息) | | 验证 | 90 (3.7%) |
| 对象层材料 | 397 (16.2%) | | 迁移 | 51 (2.1%) |
| 内涵 | 175 (7.1%) | | 负例 | 25 (1.0%) |
| 输入输出概念 | 143 (5.8%) | | 特征 | **13 (0.5%)** |

「特征 13、负例 25」不是我切得不好，而是**命题图里根本没有抽取特征与负例**——重切只能给已有节点换标签，无法赋予原图不具备的性质。所以必须换成**按《学习观》本体直接抽取**。

## 1. 两层结构

原书的概念体系有 73 个术语。全部当作节点类型是不可用的：LLM 在 70+ 个类型上无法保持一致，抽取质量会崩。因此分两层：

- **第一层 · 抽取本体（本规范第 2、3 节）**：LLM 实际使用的节点与关系类型。共 **18 个节点类型（5 知识 + 13 材料）+ 21 个关系类型**，每一个都必须能从文本判定。
- **第二层 · 理论词表（附录 A）**：原书其余概念（四维框架、知识坍缩、内隐学习……）。作为**参考词表**随包发布，供人查阅；当抽取对象就是《学习观》本身时，可选用它们作为附加节点类型。

**判据**：一个术语进入第一层，当且仅当它在任意学习材料里都能被判定为「这段文字属于该类型」。像「四维框架」「内隐学习」这类，只在讨论学习理论时才出现，不能作为通用抽取类型。

**知识 vs 材料分开建**（已确认）：书中「内涵描述 / 特征描述」是**上层材料**（判别上料），而「特征」是**判别依据本身**。二者混为一个节点，就看不出「只给了描述、没提炼出特征」——而「特征拆分」（从内涵描述拆出特征描述）正是原书给出的改进技法。因此材料与知识各建节点。

> **抽取对象已确认**：从**任意学习材料**抽取《学习观》式知识图。把《学习观》本身当材料跑，得到的就是《学习观》的知识图；换一份物理教材，得到的就是物理的知识图。附录 A 的理论词表**不**作为默认抽取类型。

## 2. 节点类型（18）

`层` 列指该节点在模型的下上结构中的位置；`—` 表示它是材料或模型整体，不占层。

### 2.1 知识结构（5）

| id | 中文 | 定义（原书） | 层 | 出处 |
|---|---|---|---|---|
| `concept` | 概念 / 范畴 | 代表一群特定现象的类别；相较对象层的元素更抽象的元素。 | 上层 | 概念提要@136、@569 |

| `rule` | 规律 | 多个对象间关系所共享的关系；上层规律是能被下层所有对应关系共享的映射规律。 | 上层 | 概念提要@1410、@3115 |

| `connection_model` | 联结模型 | 已划分出的类别之间的映射；据一个类别的具体状态推测另一个类别的具体状态。 | — | 概念提要@2127、@2133 |

**耦合关系**（原书第 34 章「描述知识」）：一个实用知识通常拆成三个模型——输入概念的判别模型、输出概念的判别模型、以及输入到输出的联结模型。抽取时应尽量凑齐这三者，它们的缺失正是诊断依据。

### 2.2 学习材料（13）

**图 34-2 原样复原**（用户提供原图后校正，此前按正文重建的版本有误）：

```
学习材料
├── 判别材料
│   ├── 判别上料 ── 内涵描述 ─┬─ 特征描述
│   │                        ├─ 特征对比
│   │                        └─ 特征类比
│   └── 判别下料 ─┬─ 正例 负例
│                 ├─ 对比例组
│                 └─ 外延对比 ── 相等、包含、相交、互斥
└── 联结材料
    ├── 联结上料 ─┬─ 关系材料 ─┬─ 关系类型 ─┬─ 常量映射
    │             │            │            ├─ 基本关系 ── 线性、周期性等
    │             │            │            └─ 关系组合
    │             │            ├─ 关系对比
    │             │            └─ 关系类比
    │             ├─ 因素材料 ── 输入、输出、表征
    │             └─ 性质材料
    └── 联结下料 ── 分段例组
```

**这张图纠正了一个重要错误**：`判别材料 / 联结材料` 才是「学习材料」的第一层切分，而 `上层 / 下层` 是**另一个正交的切分**（概念提要@2984、@2986 定义的上层材料/下层材料）。一份材料同时具有两个坐标：

- `modelKind`：`discrimination` 判别 / `connection` 联结
- `layer`：`upper` 上料 / `lower` 下料

所以「正例」的完整身份是「判别下料」，「关系材料」是「联结上料」。此前把材料按「上层材料 / 下层材料」单轴分类是错的。

| id | 中文 | modelKind | layer | 定义（原书） | 出处 |
|---|---|---|---|---|---|
| `intension_description` | 内涵描述 | 判别 | 上料 | 直接表述共有属性（内涵）的上层材料；只要某现象具备此内涵，就一定是对应概念。 | 概念提要@3751、@3703；图34-2 |
| `feature_description` | 特征描述 | 判别 | 上料 | 直接描述特征的上层材料（简称「特述」）。满足此特征**不一定**是对应概念，不满足则一定不是，只要是这个概念的现象一定具备此特征。 | 概念提要@3757；第 32 章 |
| `positive_example` | 正例 | 判别 | 下料 | 展示的输出结果是正概念的判别例述。 | 概念提要@3769 |
| `negative_example` | 负例 | 判别 | 下料 | 展示的输出结果是负概念的判别例述。 | 概念提要@3771 |
| `contrast_group` | 对比例组 | 判别 | 下料 | 一组特定的例子：一个既是 A 的正例又是 B 的负例，另一个既是 B 的正例又是 A 的负例。 | 概念提要@3773 |
| `extension_contrast` | 外延对比 | 判别 | 下料 | 对比概念外延的判别材料，子类为相等、包含、相交、互斥（`extKind` 属性）。 | 图34-2 |
| `relation_material` | 关系材料 | 联结 | 上料 | 交代输出变量如何随输入变量改变而变的材料。子类：关系类型（常量映射 / 基本关系 / 关系组合，`relKind` 属性）、关系对比、关系类比。 | 概念提要@3867；图34-2 |
| `factor_material` | 因素材料 | 联结 | 上料 | 交代某知识的输入变量、输出变量和中介变量是什么的联结材料（输入、输出、表征）。 | 概念提要@3863；图34-2 |
| `property_material` | 性质材料 | 联结 | 上料 | 交代特定类别（概念）具有的性质的材料。 | 概念提要@3885、@3887；图34-2 |
| `segment_example_group` | 分段例组 | 联结 | 下料 | 一组例子，分别展现复合关系中每个子关系的联结下料。 | 概念提要@3889；图34-2 |
| `verification_material` | 验证材料 | — | 下料 | 用于验证所建模型可泛化性的下层材料：先给输入要求推测输出，再呈现实际输出。 | 概念提要@3593；第 31 章 |
| `data_or_experience` | 数据 / 经验 | — | 下料 | 尚未 / 已明确信息推测任务的原始下层材料（`stage` 属性区分二者）。 | 概念提要@2990、@2992 |
| `memory_material` | 记忆材料 | — | — | 被用于原封不动地保存的材料（是「认识材料」下与「学习材料」并列的一支，不是学习材料）。 | 概念提要@2980；第 26 章 |

**为什么 `数据` 与 `经验` 合成一个类型**：二者只差「是否已明确推测任务」，是材料成熟度的**程度**差别而非种类差别，拆开会让 LLM 在边界上摇摆。用 `stage: data | experience` 承载。

**为什么 `例子` 不作为节点类型**：原书区分「例子」（某个知识的具体推测过程）与「例述」（叙述例子的文字材料）。抽取对象是**文本**，抽到的是例述。例子是被例述指涉的对象，落在 `refersTo` 属性里。

**为什么 `规述 / 例述` 不作为独立节点类型**：它们是「上层材料 / 下层材料」的**通用名称**（概念提要@2998、@3000），而图 34-2 给出的是**具体种类**。一个 `feature_description` 本身就是规述。让具体种类承载节点、用 `layer` 表达上/下，避免同一段文字在「规述」与「内涵描述」之间反复摇摆。

**为什么 `特征对比 / 特征类比 / 关系对比 / 关系类比` 不作为节点类型**：它们是**技法**（对已存在的节点做对比或类比），建模为关系 `compares_feature` / `compares_relation` 更贴切，用 `mode: contrast | analogy` 区分。图 34-2 把它们挂在材料树下，是因为材料可以「就是一次对比」；但抽取时把它们建成边，才能表达「对比的是哪两个特征」。

### 4.1 诊断是怎么算出来的（实现约定）

诊断由 `src/kg-ontology.mjs` 的 **`diagnoseLearningView(graph, profile)`** 计算——一个自足函数（无闭包引用），因此 `scripts/gen-ontology-inline.mjs` 能用 `Function.prototype.toString()` 把它内联进沙箱宿主；宿主不能 `import`，这是"一份实现、两处可用"的做法，而不是抄两份。

几条刻意选择的语义，都是被测试逼出来的：

- **上料/下料只数材料，不数知识节点**。`concept`/`feature`/`rule` 自身的 `layer` 也是 `upper`；若把它们算作"上料邻居"，一个光秃秃的概念会自己给自己当上料，从而掩盖真正的下层丢失。
- **缺验证按连通分量判定**，不按单个知识节点。"有学习材料但无验证材料"说的是这个知识簇，挂在父节点上的验证材料同样算数。
- **判联错配不惩罚"只建了判别模型"**。绝大多数单个概念本来就只有判别模型，若以此报警，诊断会退化成噪音。真正错的是**模型与材料的归属不一致**：`connection_model` 底下挂 `positive_example`（判别下料）。
- **每个声明的诊断都必须可被触发**。`scripts/kg-ontology-diagnostics-smoke.mjs` 里有一组图字面量，既正向断言该报的会报，也反向断言**一个构建完整的知识簇必须一条都不报**。

## 5. 抽取契约（硬性要求）

1. **一节点一命题**：一个节点只承载一个概念、一条规律或一个材料，多个判断必须拆开。
2. **材料必须有原文锚点**：`paragraph` 必填，`quote` 逐字来自原文。规律与概念允许 `quote` 为空（可能是归纳产物），但此时必须给出 `derivedFrom`（由哪几条材料归纳而来）。
3. **不得编造材料**：下层材料与验证材料只能来自原文。原文没有的例子，绝不生成——这正是「言存义空」的成因。若某规律在原文中没有例子支撑，就让它**没有** `exemplifies` 边，并产出 `lower_missing` 诊断。
4. **验证材料必须落在靶图下层之外**：若一段验证材料同时也是该知识的例述，标 `is_recycled_as`，并产出 `verification_recycled` 诊断。
5. **区分信息与知识**：只能原封不动使用的（人名、数值、术语表、操作规程）标 `memory_material`，不得因为「看起来像知识」就给它建规律节点。
6. **判别模型与联结模型分开建**：不要用一个「模型」节点含糊带过；两者混同会直接导致 `model_mismatch` 无法诊断。
7. **宁可缺边，不可臆造**：候选关系对只是召回提示，不是证据。孤立节点允许存在。
8. **每份材料显式标注两个坐标**：`modelKind`（`discrimination` 判别 / `connection` 联结）与 `layer`（`upper` 上料 / `lower` 下料）。图 34-2 的第一层切分是判别/联结，上/下是正交的第二个坐标，缺任一坐标都无法做坍缩诊断。

## 6. 校验规则

- `from`/`to` 的类型必须落在第 3 节声明的端点上，否则 `edge_invalid_relation`。
- `exemplifies` 的源必须 `layer=lower`，目标必须 `layer=upper` 或 `rule`；反向即 `edge_direction` 错误。
- `classifies` 的源必须是 `discrimination_model`；`maps_between` 的源必须是 `connection_model`。
- 同一 `from`+`to`+`relation` 只保留一条。
- `rule` 节点若既无 `exemplifies` 入边又无 `states_mapping` 入边，产出 `lower_missing`；`concept` 若只有正例无边，产出 `negative_example_missing`。

## 7. 与现有插件的关系

- **沿用**：存储（`graph_nodes`/`graph_edges`/`graph_revisions`/检查点/恢复）、抽取与审校流水线、工作台渲染、导出（JSON/CSV）、增补与轨迹模式。
- **替换**：本体层。要改成 profile 驱动——节点/关系类型、别名、证据要求集合、客户端标签、布局启发式，全部由 profile 提供。
- **文档记录本体**：在 `documents.graph_meta_json` 里写入 `ontology` 字段（无需改表结构，已有 `ensureColumn` 加法迁移）。增补抽取必须与原文档本体一致，否则拒绝。
- **已删除**：先前的纯本地渐构模式。移除内容包括 `src/kg-jianggou.mjs`、`lib/kg-jianggou.mjs`、`scripts/kg-jianggou-{cli,smoke,route-smoke}.mjs`、`docs/jianggou-split-mode.{md,schema.json}`、客户端面板与模式切换器、`jianggou-split` 的两条路由与构建期形状校验，以及对应的 npm 脚本与 README 章节。

**本体的承载方式**（实现细节，供后续维护）：DSH 的动态插件沙箱不提供 `import` / `require`，宿主半必须以单文件自足。因此 `src/kg-ontology.mjs` 是**唯一撰写来源**，它的数据由 `scripts/gen-ontology-inline.mjs` 内联进 `src/index.host.js` 的标记区块；`npm test` 会跑 `gen:ontology -- --check`，改了 profile 却没重新生成会直接失败。宿主内的查找是在内联数据上的薄封装（按需记忆化），没有异步加载、没有 await。

**两套传输，一份本体解析**（重要，踩过一次坑）：本插件有两条传输路径。动态沙箱路径注册 `harness.handle` 回调（`src/index.host.js`）；而持久化构建（`scripts/build-lib.mjs`）会把**整个 RPC 区块替换成手写的 HTTP 路由**——也就是说，`dsh web` 实际执行的是 `build-lib.mjs` 里那份平行实现，不是 `index.host.js` 里的 handler。

这个结构曾导致本体层只加在 `index.host.js` 上，于是**用户在界面上发出的每一次抽取都会静默退回命题本体**，《学习观》本体从唯一可用的 UI 完全不可达，而当时的测试全绿。修法是：本体解析收敛成两个具名 helper（`resolveTaskOntologyHost` / `continueOntologyHost`），放在共享区块里，两条传输都调用它，绝不各自重新推导。`scripts/kg-ontology-transport-smoke.mjs` 在真实 Cordis 上下文里启动**持久化构建**、捕获其路由、用打桩的模型跑一次完整抽取，专门守住这条路径——只测动态 handler 的测试抓不到这类漂移。

**布局表也是本体数据，且必须跨过 worker 边界**（第二处同类坑）：客户端的分层布局原先写死了命题关系集合——`layeredRelationWeights`（12 个关系的权重）、`reasoningRelations`（`causes`/`infers`）、`satelliteRelations`、`directionalRelations`、`strongLocalRelations`、`branchRelations`。这些其实是 profile 里 `relationTypes[].family` 与 `.weight` 的逐字副本。后果是：一张《学习观》知识图里**每个关系都落到兜底权重 2、且没有任何 family**，于是没有主干道、没有卫星吸引、没有分支道，图退化成一张毫无结构的力导向毛线团——而所有测试依然全绿。

修法与传输那次同构：不再复制本体数据，改为从载荷的 `relationTypes` 现算（`applyLayoutProfile`），未声明 family 的关系不进入任何集合（它照常画线，只是不参与布局）。命题兜底值保留在 `PROPOSITION_RELATION_LAYOUT` 里，且 `scripts/kg-semantic-layout-smoke.mjs` 会逐条核对它与 `src/kg-ontology.mjs` 的一致性，防止两边漂移。

布局跑在 **Web Worker** 里（`computeGraphLayoutAsync` → `graphLayoutWorkerSource()` 用 `Function.prototype.toString()` 把布局函数序列化进 Blob）。worker 是独立全局作用域，模块级绑定在那边是 `ReferenceError`——这个错误是被 `npm test` 当场抓到的，不是靠肉眼。因此布局表按既有惯例（`LAYER_Y_GAP` 等）在构造 worker 源码时以字面量注入，取值时机正是「为这张图请求布局」的瞬间，天然带上该文档的本体。**任何新增的、被布局函数引用的模块级数据，都必须同时加入这个注入列表。**

**知识与材料的划分是载荷里的显式字段**（`kind`）：本体载荷的每个节点类型带 `kind: 'material' | 'knowledge'`。客户端**不得**从 `layer` / `modelKind` 反推这个划分：那是另一个正交的东西，`memory_material` 两个坐标都是 `none`，而 `concept` 的 `layer` 是 `upper`（它在抽象层，但它是知识）。反推过一次，结果是按声明顺序碰巧才对。

但 `kind` **只对真正采用这个划分的本体输出**（判据：该 profile 声明了 `layer` / `modelKind` 坐标，也就是客户端会画坐标网格的那些本体）。原因是它取自 `evidenceRequiredTypes`，而这两件事**并不等价**：命题本体的 `evidenceRequiredTypes` 是「必须锚定原文」——里面是 `claim`/`inference`/`rule`，反而**不含** `example`。若照搬过去，`claim` 会被标成「学习材料」，每一个命题节点类型都会被标错。所以命题本体的载荷里根本没有 `kind` 字段，`kg-ontology-client-smoke.mjs` 会盯住这一点。

**材料坐标网格**：工作台与轨迹视图的图例下方会画出 图 34-2 的两个坐标——判别上料 / 判别下料 / 联结上料 / 联结下料，外加「其他材料」（验证材料、数据或经验、记忆材料，它们不同时具备两个坐标）与「知识」。每格显示节点数，悬停给出按类型的明细，点击定位到该格第一个节点。**只有声明了坐标的本体才渲染这个网格**，所以命题本体的界面完全不变。这个网格存在的理由是：规范承诺每份材料都落在两个正交坐标上，而在它之前界面上读不到这两个字段——判别下料的问题和联结上料的问题长得一模一样。

**抽取流水线不止一次调用模型，每一次都要跟文档本体**（第三处同类坑，也是最贵的一次）：一次抽取要跑多趟模型——首轮分块拆分、机制覆盖复核（`COVERAGE_SYSTEM_PROMPT`）、关系补全（`RELATION_WEAVE_SYSTEM_PROMPT`）、以及「验证知识图」功能的审校（`VERIFY_SYSTEM_PROMPT`）。本体层最初只改了**首轮**那个 prompt，其余几个仍是写死的命题版。

后果在第一次真机验证（原书第 4437–4997 段，560 单元、约 40 分钟、35 万输出 token）暴露：跑完所有分块、关系和审校之后，验收阶段报 `invariant_violation`，列出 12 个非法类型节点（`claim` ×10、`example` ×2），整个 run 作废、什么都没写入。两个来源：

1. **模型照抄 prompt 里的 JSON 例子。** 覆盖复核 prompt 第 9 条写的是 `{"id":"m1","type":"claim",...,"relation":"causes"}`——模型忠实地输出了 `m1、m5、m7…` 这些 id 和 `claim` 类型。**prompt 里的示例就是最有力的规格**，写错了示例等于写错了规格。
2. **宿主自己的确定性启发式注入了命题类型节点。** `explicitLimitationSeedCandidatesHost` 写死 `type: 'claim'` 造「限制结论」种子节点，`renumberNewIds` 再把它编号成 `n72、n351、n640…`。

还有一层放大器：覆盖复核路径调用 `normalizeGraph` 时**没传本体**，于是 `claim` 按命题别名正常通过（它对默认本体是合法的），一直等到**本体感知的**验收关卡才被拦下——而那一关是致命的。也就是说，一处漏传本体，把「丢掉一个坏节点」升级成了「整次抽取作废」。

修法四条：

1. `normalizeGraph` 的四个调用点**全部**传文档本体。现在非法类型在归一层就被丢掉并记 warning，不会再拖垮整次运行。
2. 覆盖复核与关系补全各自新增 `LEARNING_VIEW_*_SYSTEM_PROMPT`，**类型/关系清单与 JSON 示例都从 profile 现生成**，示例里的类型不再是写死的 `claim`。
3. 命题专属的确定性启发式（限制结论种子）在非默认本体下**直接不启用**——它编码的是命题语义，对应的能力由该本体的覆盖复核 prompt 承担（在《学习观》里一句限制结论该建成 `rule`）。
4. 契约新增 `ontologyPipelinePrompts`，把每一趟的 prompt 都暴露出来，`kg-ontology-prompt-smoke.mjs` 逐趟检查：不得出现别的本体的 `id 中文` 清单行，不得在 JSON 示例里出现别的本体的 type/relation。**这个检查做过反向验证**——故意把 `claim` 塞回《学习观》覆盖复核 prompt，测试立刻失败。

教训与前面几处一致：本体不是「首轮 prompt 的一个参数」，它是**整条流水线的前提**。任何一趟模型调用、任何一个归一层、任何一段序列化到别的执行环境里的代码，只要它知道类型名，就必须从本体解析，而不是自己重新写一份。

### 7.1 流停顿要重试一次，绝对超时不要

真机验证暴露的另一个问题与本体无关，但它同样会让整轮抽取作废：**模型流静默 180 秒会被判为 `timeout`，而所有阶段都把 `timeout` 当终止错误**，于是外面那些重试循环根本没机会跑。第一次跑 560 单元时，抽取与关系补全都做完了，却在关系语义审校（48/392）被一次服务商卡顿终止，四十多分钟作废。

`reasoning-delta` 与 `text-delta` 都会刷新这个空闲计时器，所以「静默 180 秒」意味着模型真的一无所出——那是传输层的抖动，不是对材料的判断。因此改动很小：在 `callExtractionModel` 里对**空闲流停顿**重试一次（间隔 3 秒），并把这条路径钉死在 `kg-extraction-stall-retry-smoke.mjs` 上——它同时也验证「永远卡死」的情况只会打两次请求就失败，不会无限重试。

刻意**保持**的边界：绝对超时（`llm_stream`，模型已经流了 15 分钟但没结束）**不重试**。那是真正昂贵的情形，重放它大概率再花 15 分钟。所以这是一条有区分的契约，而不是「超时就重试」：

| 情形 | 判据 | 行为 |
| --- | --- | --- |
| 空闲流停顿 | `phase === 'llm_stream_idle'` | 重试 1 次 |
| 绝对超时 | `phase === 'llm_stream'` | 不重试，直接失败 |
| 用户取消 | `code === 'cancelled'` | 不重试 |

`kg-timeout-cancellation-smoke.mjs` 原本断言「超时一律不得自动重试」。这条契约这一次被**有意修改**了：断言现在区分上述两种情形（空闲停顿恰好重试一次，绝对超时一次都不重试）。改动前先做了反向验证——把重试去掉，新测试立刻以「a single idle stall still failed the run」失败。

### 7.2 真机验证结果（原书）

在原书（213305 字、5413 段）上跑两次真实抽取，分别覆盖本体的两个坐标分支。模型为 deepseek-flash，产物落在 `scripts/tmp/`（含原文，已 gitignore）。

| --- | --- | --- |
| 窗口 | 283 单元 / 9318 字 | 160 单元 / 6097 字 |
| 耗时 | 54 分钟 | 36 分钟 |
| 节点 / 边 | 254 / 286 | 165 / 196 |
| 知识 / 材料 | 139 / 115 | 98 / 67 |
| **未声明类型** | **0** | **0** |
| **未声明关系** | **0** | **0** |
| **无锚点节点** | **0** | **0** |
| 节点类型覆盖 | 16 / 18 | 15 / 18 |
| 关系覆盖 | 15 / 21 | 18 / 21 |
| 触发的诊断 | `lower_missing(48)` `verification_missing(48)` `meaning_without_words(17)` `model_mismatch(3)` `upper_missing(1)` `words_without_meaning(1)` | `verification_missing(44)` `meaning_without_words(23)` `lower_missing(22)` `words_without_meaning(6)` `upper_missing(3)` `layer_mismatch(2)` |

**两次合并**：节点类型 **17 / 18**，关系 **18 / 21**。合计 419 个节点、482 条边，**未声明类型 0、未声明关系 0、无锚点节点 0**。

结论：

1. **本体闭合成立**：两次运行合计 419 个节点，没有一个落在 18 类之外，也没有一条边落在 21 类之外。这是本节那四处修复的直接效果——修复前同口径的运行在验收阶段整体作废。
2. **材料没有被编造**：全部节点带真实段落锚点、`quote` 可回溯。本体最想防的「言存义空」在产物层面没有发生。
3. **知识层 5/5 两窗口都全中**（`rule`、`concept`、`feature`、`discrimination_model`、`connection_model`），「知识与材料分开建节点」不是纸面设计；两个坐标分支各自用得最多的类型也确实不同。
4. **始终未出现的 1 个类型是 `segment_example_group`（分段例组）**，**3 个关系是 `is_recycled_as`（例习互转）、`maps_between`（联结映射）、`transfers_from`（迁移）**。`transfers_from` 是刻意保守（§8 待定 1）。
   - `is_recycled_as` 为 0 经核对是**正确结果**，不是漏抽：它记录的是「例子被转用作验证材料」这一现象，而两次运行里**没有任何验证材料的原文与某个例子重复**（A 有 27 个候选例子、3 份验证材料，B 有 36 个、2 份，重复数均为 0），独立的 `verification_recycled` 诊断同样为 0。关系与诊断是同一现象的两个视角，结论一致。窗口里没发生这件事，关系就不该有边。
   - `maps_between` 为 0 则是**真问题**，见下条。
5. **`maps_between` 之所以建不出来，是「映射只写在文字里」**：两次运行共 6 个 `connection_model`，它们只连 `has_rule` / `compares_relation` / `aligns_upper_lower`，**没有一个连到因素材料或输入输出概念**。看节点文字就清楚——「例规编排与听众观感之间的联结：输入变量是不同例规编排，输出变量是不同听众观感」「英语时态类别（过去／现在／将来）与表述类别…之间的对应关系」——两端都写出来了，却没有被建成节点。于是 `maps_between` 无从建起，`states_mapping`（唯一来源是数量充足的 `relation_material`）成了唯一出口。
6. 为此新增第 11 条诊断 **`mapping_missing`（联结空载）**：一个 `connection_model` 既没有输入输出因素材料、也没有 `maps_between` 边，就说明映射只活在它的文字里、没有任何东西可以拿来核对。新增后**在两次真机产物上回放**（诊断是纯函数，直接吃已存的图，不必重跑模型）：A 命中 2/2，B 命中 4/4，正是上面那 6 个节点。同时给抽取 prompt 补了一条硬性要求（若原文明确写出两端，必须建节点并连 `maps_between`；`factor_material` 才算数；原文没写两端不许补造），这样这条诊断才有机会从「一直亮」变成回归探针。**这条 prompt 改动尚未经真机复跑验证**。
7. **11 个诊断有 8 个在真实数据上触发**（`layer_mismatch` 只在 B 触发，`model_mismatch` 只在 A 触发），不是死代码。逐条看过 `lower_missing` 的样本后确认是**正确诊断而非误报**：命中的是「验证」「例规编排」「自动调节机制」这类**元层概念**——A 窗口在讨论材料分类本身，很多知识是抽象陈述、例子在别处。诊断如实报出了「有知识、没材料」，这正是本体的用途。

| `maps_between` 边 | 0 | **15** |
| `mapping_missing` | 4（4/4 全中） | **0** |
| 节点 / 边 | 165 / 196 | 157 / 189 |
| 未声明类型 / 关系 | 0 / 0 | 0 / 0 |
| 无锚点节点 | 0 | 0 |

15 条边全部是 `connection_model → factor_material`（输入/输出变量）或 `connection_model → concept`（输入/输出类别），**每条都带真实段落证据**，例如「万有引力定律」那条引的是「它的输入用数学语言来讲，是一个三维变量」，「例规编排」那条引的是「它们的输入和输出都是不同例规编排与不同听众观感」。9 个 `connection_model` 里 8 个建出了映射，剩下的那个走的是 `states_variable + factor_material` 这条被允许的替代路径，所以诊断正确地保持沉默。

也就是说：**诊断 + prompt 是一对**——诊断指出坍缩，prompt 负责不再坍缩，复跑证明这条诊断能从「一直亮」变成回归探针。运行间有自然波动（`verifies`、`compares_relation` 这次没出现），所以判断只看 `maps_between` 与 `mapping_missing` 这两个直接指标。

### 7.4 第四处同类坑：属性在归一层被丢掉

复跑时顺手核对了一件事：**189 条边没有一条带 `role`**。查下去发现 `normalizeGraph` 构造边时只复制 `fromNodeId / toNodeId / relation / evidence`，节点同理——模型输出的任何其他字段都在这里被丢弃。

这与前三处是同一类错误，而且对本体的伤害很直接：本规范**用属性定义了若干关系的语义**——

| 关系 | 靠什么属性承载语义 |
| --- | --- |
| `maps_between` | `role: input / output`（哪端是输入） |
| `contrasts` / `extension_relation` | `role: positive / negative`（两条边分正负） |
| `compares_feature` / `compares_relation` | `mode: contrast / analogy`（对比还是类比） |
| `data_or_experience` | `stage`（数据还是经验） |
| `relation_material` | `relKind`（常量映射／基本关系／关系组合） |

prompt 里写着「用 role 区分 input / output」，模型照做与否，**在这个归一层之后完全看不见**。修法是让本体自己声明这份属性词表（`edgeAttributes` / `nodeAttributes`），归一层只复制声明过的键、其余一律拒绝：

- 《学习观》声明 `edgeAttributes: ['role', 'mode']`、`nodeAttributes: ['stage', 'relKind']`；
- 命题本体**什么都不声明**，因此它的图逐字节不变（这是刻意的向后兼容，`kg-ontology-extraction-smoke.mjs` 会盯住「未声明的属性不得被复制」）。

词表放在本体里而不是写死在归一层，理由与前几处一致：归一层不该知道某个本体用哪些属性表达语义。

**真机确认**：修好之后在同一个 B 窗口再跑一次（161 节点 / 204 边，约 37 分钟），**204 条边里有 25 条带属性**（修复前是 0 条）：

| 属性 | 分布 |
| --- | --- |
| `maps_between` + `role` | input 7 · output 9（另有 4 条模型没写 role） |
| `compares_feature` / `compares_relation` + `mode` | contrast 8 / contrast 1 |

所以模型确实会输出 `role`/`mode`，之前的「看不见」纯粹是归一层吃掉了。`stage` / `relKind` 这一轮没出现——那个窗口没用到 `data_or_experience` 与关系材料的子类，属正常。未声明类型 0、未声明关系 0、无锚点节点 0，`maps_between` 20 条、`mapping_missing` 0。

**属性的呈现**：值标签也放在本体里（`edgeAttributeLabels`），随载荷下发，客户端据此把属性拼到边的标签上——`maps_between role=input` 画成「联结映射·入」，而 `compares_feature` 的中文本来就是「特征对比/类比」，属性把它收敛成「特征对比/类比·类比」。所以命题本体声明零属性、也就零后缀，图与改动前逐字一致；未知属性值一律不显示（不猜）。详情卡里则按 `role=input` 原样列出。另外，第一次跑完整窗口（560 单元）时，抽取与关系补全都已完成，但在**关系语义审校**阶段（48/392 条）撞上模型侧 180 秒无输出而中止——那是服务商流式卡顿，不是本体问题（`reasoning-delta` 会刷新该超时，所以 180 秒静默意味着真的一无所出）。这也说明该阶段对长文档很贵：560 单元会产生 392 条待审关系。

## 8. 已定与待定

**已定**（用户确认）：

1. **抽取对象 = 通用**：从任意学习材料抽《学习观》式知识图。原书那 73 个理论概念不作默认抽取类型，仅作附录 A 参考词表。
2. **知识与材料分开建节点**：`intension_description`/`feature_description`（上层材料）与 `feature`（判别依据）各自成节点，以便诊断「只给了描述、没提炼出特征」。
3. **「规律」采用概念提要@3115 的定义**（可被下层所有对应关系共享的映射规律），与下上结构一致；@1410 的措辞视为同义。
4. **「记言待学」与「记言代学」合并**为一个诊断码，中文取「记言代学」（第 34 章的「记言待学」未给定义，疑为异写）。
5. **材料分类以图 34-2 原图为准**：第一层切分是 `判别材料 / 联结材料`，`上层 / 下层` 是正交的第二个坐标（已按原图校正 §2.2）。据此新增 `extension_contrast` 外延对比、`property_material` 性质材料、`segment_example_group` 分段例组三个类型。

**待定**：

1. **`transfers_from` 的端点**：原书把迁移定义为「复用既有模型」这一行为，而非静态关系，抽取时容易过度建边。要求 `evidence` 出现显式复用语义才建边；实测噪音大则降级为节点属性。
2. **正例/负例的目标**：本规范让它们指向 `concept`，用边的 `role: positive|negative` 区分。原书另有「正概念/负概念」一对术语；若实测需要独立节点（例如同一概念在不同材料里正负颠倒），再拆。
3. **`relation_material` 的子类**：图 34-2 把关系类型细分为常量映射 / 基本关系 / 关系组合。目前用 `relKind` 属性承载，不建子类型；若实测需要按子类型查询，再拆。
4. **`data_or_experience` 是否再拆**：目前用 `stage` 属性区分「数据 / 经验」。若实测 `stage` 判定不稳，退回两个节点类型。
5. **`segment_example_group` 是否该保留**（§7.2 实测发现）：两次运行都没用到它。图 34-2 里它是「联结下料」，但真机上联结分支的分段例子被建成了 `positive_example` 或 `data_or_experience`。要么在 prompt 里写清它和正例的分工（分段例组是「一段输入序列对应一段输出序列」的例子），要么承认它在本体里是多余的、并入正例。
